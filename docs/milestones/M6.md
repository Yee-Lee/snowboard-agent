# M6 — Vision／Look 與獨立 VLM POC

產品主線：`M5.tool → M5 MQTT → M6 Look → M7 → BETA`。
M6 先採 YOLO；VLM 研究不阻擋產品主線。Wake 移出目前範圍，BETA 前再決定是否加入。

## 1. 已確認流程

```text
listen → 原對話 Gemma 選 Look → speak「我看一下。」
→ 下一輪 look-only：Camera → YOLO → 結果整理 function
→ 觀察＋「依本次結果回答先前問題」→ 原對話 Gemma → speak → listen
```

Look 是 perception；模型可選擇此能力，Core 不新增 action=look。
該輪不等待 listen，不替換正常的對話 Conversation。前文與模型意圖由原 Conversation
保留，接續品質須實測。本輪不考慮 read／Look 交錯。

## 2. YOLO 產品路徑

### 2.1 價值與範圍

先提供有根據的物件觀察，沿用 M3 Camera HAL 與 M5.tool 的路由／輸入接面。
真相機、YOLO runtime 與 Pi 共存是新增工作，不能用 mock Accepted 代替。

### 2.2 結果整理 function

Camera 由 Look worker 持有；Vision adapter 收取影像，執行 YOLO 與確定性的整理，
回傳 VisionResult.text，再由 Look 發 PerceptionResult(kind=look)。Reasoner 加上來源、
狀態與接續提示；整理 function 不再呼叫 LLM。

- 輸入為模型實際輸出的 class、confidence、bounding box；依部署設定篩選並固定排序。
- 依 class map 命名；數量與粗略畫面位置可由結果推導，確切輸出在模型選定時固定。
- 形成有界、可解析的文字 facts，不把推導資料冒充模型原始輸出。
- 成功但空偵測是「沒有辨識到」，不代表物件不存在；與相機／推論失敗分開。
- 不憑空加入顏色、OCR、身分、真實距離、活動理解；本輪不為顏色另加 OpenCV 或
  segmentation 系統。未來有產品需求再評估。
- 畫面左／右不等於使用者左手邊；confidence 不作為對使用者保證的真實機率。

Gemma 只能根據提供的 facts 回答，不能補出未提供的杯子顏色或書名。

### 2.2.1 YOLO 能力取捨與 LLM 輸入（M6 設計提案）

YOLO 是模型系列，能力取決於選定的 task、weights 與 class map；不能把系列所有功能
當成同一模型的輸出。M6 只需要一般 **object detection**：每個候選物件的類別 ID、
confidence 與軸對齊 bounding box。篩選後由程式計算支援物件的數量及畫面左／中／右。
不使用分類整張圖、instance／semantic segmentation、pose、tracking、旋轉框或 depth；
它們目前沒有對應的產品問題，會增加模型、資料或 Pi 資源成本。顏色、OCR、身分、
真實距離與行為也不從 detection 結果推論。

**資料分層**：

```text
模型內部：class_id + confidence + box_xyxy
  → 確定性篩選、class map、計數與畫面區域整理
VisionResult.text：有界的觀察 facts（不含 raw box、數值 confidence 或影像）
  → 既有 Look projector：source/status/facts/instruction 四欄 JSON
  → 原 Conversation 的 Gemma 回答先前問題
```

建議的 `facts` 是緊湊、固定欄位的 JSON **字串**，沿用既有
`VisionResult.text` 與最多 512 normalized code points 的接面；外層 wrapper 的
`facts` 型別仍是 string，不直接改動 M5 已驗收的 transport。例如：

```json
{"source":"look","status":"ok","facts":"{\"observations\":[{\"name\":\"杯子\",\"count\":2,\"positions\":\"畫面左側1個、畫面中央1個\",\"certainty\":\"較明確\"},{\"name\":\"書\",\"count\":1,\"positions\":\"畫面右側1個\",\"certainty\":\"不確定\"}]}","instruction":"優先回答先前問題，不列無關物件；count是合計數量，positions要逐處對應，不可把總數說成在同一位置。certainty=不確定的物件名稱前必須說「可能」，certainty=較明確可直接陳述。未知屬性說不知道。空observations固定回答：這次沒有辨識到支援的物件。不得說沒有任何東西。text最多30字。"}
```

空偵測的 `facts` 用 `{"observations":[],"note":"本次沒有辨識到支援的物件"}`，
不可解讀成畫面沒有物件。`certainty` 以「較明確／不確定」表達主要／次要信心層級，
並非模型原始機率，也不是物件在場景中的重要性。先選取最多三個實體框，再依類別與
信心層級彙總 count；positions 列出各區域的數量，不能先分組後才限制三項。
框中心 x 小於 1/3 為左側、1/3 至小於 2/3 為中央，其餘為右側。
公開輸入不含檔名、原圖、box 座標、
數值 confidence、未支援類別或任意模型文字。現有 M5 instruction 仍是「只說物件種類」；
M6 要允許數量／畫面位置與主要／次要用詞時需
更新為本節專屬版本，並以實際 Gemma 接續與 context admission 確認它可用。
Look 結果送回同一 Conversation 時，以當輪 constrained JSON schema 將 intent enum
限制為 `speak`，不靠提示防止空偵測誤選 `end`；listen 輪保留原 schema。
Look 回答沿用既有 semantic validator 的 30 字上限，這一輪 instruction 明示最多30字；
原問題、合計數量、逐區位置與次要候選的不確定措辭仍由 Pi 探針確認。

### 2.3 Entry

M5 Accepted 後，在 model_spec.md 固定 YOLO 任務／版本、weights、class map、輸入格式／
尺寸、runtime、授權、Pi 安裝與必要量測。選定 YOLO26s 的設計輸入見 model_spec.md §7。
固定相機 fixture、整理政策、輸入上限、timeout 與資源需求，再交 Test Spec。
不依賴 Wake IPC、VLM POC 完成或再次 baseline selection。

### 2.4 驗收問題

| 問題 | 最低證據 |
| :--- | :--- |
| 使用本次影像 | 固定場景改變，偵測與回答跟著改變 |
| 回答有依據 | 能答已供資訊，誠實處理未知屬性與空偵測 |
| 自動接續 | look-only 無需新語音，原問題可接續，回答後 listen |
| Pi 可運作 | Camera／YOLO 與 Audio／Gemma 的實際記憶體及等待時間 |
| 受影響錯誤可收斂 | capture／inference error、timeout、中斷與 stop 的相關資源釋放 |

只做新增功能與受影響回歸，不加入原 M6 的固定 20-session soak、全能力矩陣或 Wake 驗收。
Pi 上同一待提交內容完成適用自動、硬體與人工判讀；反應時間依 §5.4 D5 的
Pi POC 量測固定 timeout／等待界線，再於 V4 驗證。

## 3. 獨立 POC：Camera + VLM 描述 → LLM

### 3.1 研究目的與分工

USER 同意值得開 POC；本節提供研究範圍，尚未執行或對外送件。
優先研究現有 Gemma 4 E2B／LiteRT-LM，評估是否可取代 YOLO 及額外手寫屬性分析。

```text
Camera → VLM＋固定描述 prompt → 影像內容描述
       → 原對話 LLM＋接續提示 → 最終回答
```

VLM 只描述畫面；原對話 LLM 保留產品身分與前文。不用圖片直接送入原對話的一次推論
替代這個兩段方案。M5.tool mock 描述只驗接續，不證明 VLM 可用。

### 3.2 最小研究內容

1. **部署**：目前模型檔／LiteRT-LM 在 Pi 設定 vision backend、前處理並送入固定影像。
   記錄實際 API／設定變更，不先假定需要修改底層 runtime。
2. **模型共用**：先讓對話 Conversation 記住問題，再以獨立視覺 Conversation 描述圖片，
   回原 Conversation 回答。檢查同 Engine、兩 Conversation、依序推論是否可行，以及前文
   是否保留。若需另一個 Engine／模型副本，明列記憶體成本，不靜默替換實驗。
3. **品質**：少量固定場景涵蓋物件、主要顏色、位置及看不清楚；檢查描述捏造／資訊遺漏
   與下游回答。以相同影像及問題比較可取得的 YOLO 路徑，不新建大型 benchmark。
4. **成本**：記錄首次／後續視覺與回答時間、Pi 記憶體、影像及 context 成本；只做直接
   必要的中斷／清理檢查，確認不破壞原對話。現行 1024-token context 不推定適用影像。

描述 prompt 要求可見物件、可辨識主要顏色、粗略位置／明顯關係及不確定處；不猜不可見
內容。具體長度／影像尺寸依量測選定。VLM 的兩次推論與描述資訊損失都是採用比較項目。

### 3.3 研究輸出與採用

回報可行／有條件可行／不可行或證據不足、描述與回答品質、時間／記憶體、必要 API
改動與限制。影像及內容只供 private 判讀；public 留必要量測、boolean、count、stable code。
不增加 digest assertion、全面 soak、行政 closure 或互簽。
研究結果支持後續採用決策，不自動替換 M6 baseline；YOLO 主線可繼續。
跨 repo／外部交付依實際授權與契約另辦，本文件不代表任務已對外建立。

## 4. 排除

Video／tracking、gesture、Wake、通用 reasoning loop、跨 Session 記憶、read／Look
交錯、正式 Display 動畫（M7）、systemd／OTA／release packaging 均不在本輪。

## 5. M6 Look 設計與交付計畫（2026-10-29）

本節把 §1–§2 的產品目標拆成可交付工作；選定模型、類別範圍與等待預算見
model_spec.md §7。本計畫不代替產品 Test Spec 或 Verify。每項驗證只對應可觀察的失敗風險。

### 5.1 設計順序與產物

1. **模型與輸出政策 POC**：先核對候選 YOLO 對目標物件是否有合適類別，以及模型來源、
   授權、Pi 可安裝 runtime、實際輸入／輸出格式。工作站先以一張已知內容照片確認真實
   模型可輸出 class、confidence、box，再用 §5.3 的少量標註照片比較模型與篩選／排序政策。
   Pi 對有希望的候選重跑相同照片，量測載入、推論、記憶體與溫度／節流；只有目標
   runtime 與資源可用，才在 `model_spec.md` 固定版本、weights、class map、前處理尺寸、
   runtime 與部署方式。工作站 POC 不能宣稱 Pi 可用。
2. **固定影像與偵測邊界**：沿用 `Camera.capture() -> bytes` 與 `VisionAdapter.describe(image)`；
   本輪明確配置相機格式與寬高，adapter 在推論前核對影像長度／解碼結果，依模型規格轉色、
   縮放並把輸出座標映回原影像。篩選 confidence、類別與重疊框的政策，及排序規則，
   必須在選定模型後寫成固定值；不把模型原始浮點值直接交 LLM。
3. **固定觀察 facts**：只由篩選後的偵測推導支援類別的名稱、數量及粗略畫面位置；
   位置以影像座標為準，不說成使用者的左／右。相同輸入必須得到相同順序與文字。
   輸出遵守既有非空、最多 512 normalized code points 的 Look 邊界；超限時減少列出的
   偵測細節並明示省略，不截斷文字，也不虛構顏色、OCR、身分或距離。成功空偵測使用
   「本次沒有辨識到支援的物件」。原影像與原始偵測只留必要的 private 診斷，不進公開紀錄。
4. **接回既有產品路徑**：composition 依明確配置選 mock 或真實 Vision adapter，
   保留 Look worker、Event Bus、Reasoner 與原 Conversation 接面；不另建推論回路。
   錯誤／timeout 依既有 Look 契約轉成可重試回饋。若 native 推論或相機擷取無法合作停止，
   必須有可證明已停止的隔離／資源回收方式，才可宣稱 timeout 或正常 stop；否則走既有
   ERROR／recovery，不發布正常成功或空偵測。
5. **交 Test Spec 與開發**：Designer 固定以上數值及例外邊界後，Tester 依 §5.2 的風險
   選少量可執行情境。Developer 實作後在 Pi 對待提交相同內容完成適用自動、整合、硬體
   與人工測試，Verify PASS 後才可準備 commit。

### 5.2 交付標準與驗證地點

| 產品風險／交付標準 | 工作站可完成 | Pi 必須完成 |
| :--- | :--- | :--- |
| 錯誤影像或偵測輸出被當成觀察 | 格式／尺寸檢查、前後處理與 class map 的固定向量；非法輸入走 error | 真相機影像格式、尺寸與模型輸出實際相容 |
| 物件、數量與位置描述失真 | 一張已知內容的靜態照片跑真實 YOLO 推論，檢查 class／box 與 facts；固定偵測向量驗排序、512 字邊界、空偵測與未知屬性 | 同張照片在目標 runtime 重跑；少量真相機實景改變位置或物件，確認偵測及回答跟著本次影像改變；人工判讀語意 |
| Look 後失去原問題或播出無依據回答 | mock／fixture 跑原 Conversation 接續、一次回答後回 listen、失敗時不呼叫 LLM | 真 Camera＋YOLO＋Gemma＋Audio 的完整語音流程，聽辨回答與接續 |
| Camera／YOLO 與現有產品資源衝突 | 以可控 backend 驗啟停、取消、timeout 與不發布過期結果 | 同機載入 Camera、YOLO、Audio、Gemma，記錄載入／取像／推論／回答等待及記憶體；實際中斷、stop、錯誤後可再次使用 |

工作站結果可完成純邏輯與契約的設計判定，但不能代替 Pi 硬體與產品結果。Pi 最終
Verify 仍須對待提交相同內容跑適用的自動與整合測試；只增加直接受影響回歸，不建立
全類別矩陣、長時間 soak 或每次 run 的 digest assertion。若量測顯示等待過長或資源
無法共存，先據實收斂模型／部署選擇，再固定產品可接受的數值，不以 mock PASS 代替。

### 5.3 模型與觀察政策 POC（選型用，不是產品驗收）

這是 M6 Design 內的選型活動，不新增 M6 前置 milestone、M6.yolo gate 或另一份狀態文件。
**D1–D5 全部使用靜態照片或由照片得到的固定 facts，不接真相機**：D1／D2 比模型與
政策，D3 比格式與原 Conversation 接續，D4 比 Pi 目標 runtime／資源，D5 比反應時間。真相機取像
從 V1 的產品 Verify 開始驗；D4 的同機載入探針也不宣稱完整 Look 流程通過。
可重跑的 diagnostic 腳本可放在本 repo 的 `scripts/`，並以獨立 worktree／topic
branch 隔離；不冒充產品 config 或 Test Spec。照片、模型權重、人工真值、逐張
討論、候選中英對照、原始輸出與量測紀錄均放在 Git 忽略的本機
`tests/fixtures/m6_yolo/`，不進提交。最終產品政策更新既有 M6 與 `model_spec.md`；
產品 class map／配置由後續 Developer 依定稿設計實作，
不直接把 POC 設定升格成產品 authority。分支本身不代表驗收；若要提交 POC 程式，
仍依 repo 規則完成 Pi 對相同 bytes 的適用驗證。

- **候選**：先比較 COCO 預訓練的 `YOLO11n`（成熟基準）與 `YOLO26n`
  （較新、[官方 Pi 5 ONNX benchmark](https://docs.ultralytics.com/guides/raspberry-pi/) 有資料），同用 object detection、相同 12 張照片
  與輸入尺寸；這同時回答「選哪個世代」而不遍歷 v3–v11。只有 `n` 在目標物件品質
  不足、Pi 尚有餘裕時才加入同系列 `s`。工作站逐張比較後，USER 指定
  `YOLO26s` 已完成 D4／D5 Pi 記憶體、推論等待與 Gemma／Audio 共存探針，
  選為 M6 實作 baseline，具體部署見 model_spec.md §7。開放詞彙或其他系列只在
  類別缺口／部署問題確實出現時評估。
- **照片與真值**：本輪資料集為 12 張靜態照片：5 張可追溯來源與使用範圍的
  現成照片、5 張 Pi 相機實拍照片，以及 2 張空偵測／低信心診斷照。人工逐張標記
  可見的目標類別與粗略框；整組涵蓋清楚單物件、不同大小／位置的多物件、沒有支援
  類別、容易混淆或遮擋的場景。記錄照片來源與可使用範圍；原圖不入 Git。
  D1–D5 都讀這些靜態檔案，Pi 實拍在此只取得 dataset，不代表 V1 真相機產品接線已驗。
  USER 選定的照片與來源清單集中於 Git 忽略的本機 fixture 目錄，
  逐張判讀只在該目錄保存，不寫入本設計文件。
- **比較問題**：逐張檢查有無漏掉目標物件、誤認、重複框、框位置錯誤與信心值分布。
  暫以 `0.25`／`0.5`／`0.8` 作探索性篩選比較，並比較「最多三筆」與較完整的有界 facts；
  比較按 confidence、框面積或類別／位置分組時，是否漏掉使用者可能詢問的小物件。
  `0.8` 是待試政策，不預設為正確機率或產品門檻；框面積也不是物件重要程度。
- **選定政策**：模型、類別開放範圍、中文名稱映射、門檻、去重、排序、計數與輸出上限
  必須由照片結果與 Pi 成本共同決定。輸出被裁減時明示只列出部分偵測；無合格偵測
  只說「本次沒有辨識到支援的物件」，不說畫面沒有物件。若低信心結果可能影響回答，
  優先表達本次辨識不確定，不把原始信心值交給 LLM 讓它自行解讀。USER 指定
  `≥0.75` 為主要目標標準、`0.50–<0.75` 為次要目標、`<0.50` 不採用，
  送入 Gemma 的 `facts` 最多接受三個物體；合格候選超過三個時按 confidence
  由高到低取前三框，並明示只列出部分偵測。USER 接受多物體場景因此漏掉
  一件物體的取捨；不得把低於門檻或被省略的物體說成不存在。
- **交付**：在既有 M6／`model_spec.md` 固定選定模型與產品政策；照片別判讀、
  錯誤例與 Pi 原始資源數據留於 Git 忽略的本機 fixture。這組小樣本只能支持本輪場景選擇，
  不宣稱全面準確率，也不擴成所有類別的測試矩陣。

**POC 可重跑輸入**：diagnostic 腳本讀明確指定的權重、照片與真值路徑；
本機清單逐張記錄來源／使用範圍、可見物件、主次判讀與粗略框。候選、門檻、
選中／漏掉／誤報、facts、時間與資源紀錄都留在 Git 忽略的本機 fixture；
可提交的設計只保留最後的產品決策與必要理由。此工具不在
application startup 或每次 run 計算／驗證任何 artifact digest。

### 5.4 進入 Test Spec 與 Developer 的完成條件

**Design POC 完成條件（選型依據；不是正式產品 PASS）**：

| 編號 | 要排除的設計風險 | 完成判定與地點 |
| :--- | :--- | :--- |
| D1 | 模型根本不支援目標物件，或名稱對錯類別 | 選定 task、候選 weights／版本與授權；讀出該 weights 的類別表，標明要開放的類別 ID 與中英映射。人工標註的少量照片涵蓋清楚單物件、多物件含小物件、無支援類別、遮擋／混淆。工作站可完成；缺少必要類別就換候選或縮小明示範圍。 |
| D2 | 選錯世代、規模、門檻或前三筆政策而漏報／誤報 | 同張照片比較候選模型、門檻與排序，逐張記錄主體、次要物件、誤報、重複框和被省略物件。依 USER 已定的 0.75／0.5 分級與 confidence 前三個實體框政策，記錄可接受的省略取捨；不把小樣本換算成全面準確率。工作站完成。 |
| D3 | LLM 輸入誤解或超出既有邊界 | 固定 class／數量／畫面位置整理、低信心與空偵測語意、超出清單時的省略說明；範例 `facts` 可解析、非空且 ≤512 normalized code points，沒有 raw image／box／confidence 或未提供屬性。工作站驗 formatter；Pi 用原 Conversation＋靜態 facts 探針確認 Gemma 可接續問題、回答數量／畫面位置並處理未知屬性，記錄 context admission。此處不接真相機。 |
| D4 | 選到無法在目標機部署或共存的模型 | Pi 用同一批靜態照片在目標 runtime 載入與推論，記錄 process memory 與溫度／節流；至少做一次與既有 Gemma／Audio 同機載入的有界資源探針，不需完整 Look 流程。無法安裝、OOM、無法停止或資源明顯不可用時改選候選；把選定 runtime、輸入與部署需求寫入 `model_spec.md`／本設計。 |
| D5 | 模型太慢，讓 Look 回答等待不可接受 | 工作站先記候選相對時間；Pi 對相同靜態照片分別量模型載入、首次推論、後續推論及結果整理的 wall-clock 時間，另在 Gemma／Audio 同機載入時量一次。保留逐張數值與最慢場景，不用 12 張小樣本假裝有可靠 p95。另以全新 process 比較冷首張與 startup 單次 warm-up 後首張，確認 lazy initialization 可移到 READY 前，且不在每次 Look 重做。根據 Pi 數據固定 Look timeout 與本輪可接受的等待界線；超出界線則換模型／輸入尺寸或調整產品範圍，才交 Test Spec。 |
