# M3 規劃

## 5. M3 ── Raspberry Pi HAL 與硬體 bring-up

### 5.1 範圍

* 在 Raspberry Pi 5 實作與驗證：
  * AudioInput / AudioOutput real backend。
  * Display chip driver、native build 與 `DisplayDevice` 。
  * Camera `picamera2` backend。
  * GPIO `gpiod` backend 與一 pin 一訂閱者原則。
* 實作 Ch 8 的 renderer、arbiter、slot registry、Presenter / StatusBar 最小 owner 接線。
* 實作 `display_spec.md` 的 selected profile：固定離線字型、Normal 的 StatusBar + Main、state slot、Main fixture，以及 startup / shutdown Fullscreen Blank。
* 提供 Pi local config 範例或部署說明，但不提交真實 pin、credential 或使用者絕對路徑。
* 驗證 real backend 啟動失敗時 audio / display / camera fallback null ；GPIO 不建立 NullGPIO。

### 5.2 相依

* M2 驗收通過。
* 目標硬體接線、chip 型號、ALSA device、CSI camera 與 GPIO 測試 pin 已由使用者確認。
* Pi-only dependency 與 native library 安裝方式已在模組 README 或 setup 文件記錄。
* `display_spec.md` selected profile 已納入 M3 test spec 與 Developer 工作包。

#### 5.2.1 POC contract checkpoints

M3 只依賴 Audio / Display 的 POC contract；真實 LLM 不在本階段 scope，LLM POC contract 不得被列為 M3 開發或驗收 blocker。

M3 採**單一整合進場 gate**：即使 Audio contract 已先 Accepted，也不得拆出 Audio-only、Camera-only、GPIO-only 或其他 M3 產品實作提前開工。Core 可在 Display POC contract 收斂前先完成 `display_spec.md`、mock、字型與 chip-independent 設計；但必須等 Display contract Accepted as design input，且 arch / implement / milestone / Display profile 在同一 M3 Design Ready gate 通過，再完成 test spec 簽核與 Developer 工作包，才正式進入 M3 開發。

| Checkpoint | Audio | Display | 放行規則 |
| :--- | :--- | :--- | :--- |
| **Core Display design review** | Core 已將 Audio contract 採用為設計輸入；不影響介面的驗收條件可保持 pending，但須有 owner 與 deadline | POC pending 不阻擋 `display_spec.md`、mock、字型與 chip-independent contract review；不得把 draft POC 寫成 real-backend baseline | Designer 記錄 Core-owned disposition 與 POC-owned pending condition |
| **M3 Design Ready 前** | Audio design input 維持 Accepted with Conditions | 必須取得可直接對齊 Ch 2a / Ch 8 / Ch 10 的 Accepted design input；lifecycle、ABI、fixture 或 evidence interface blocking finding 均須先解決 | Designer 在 `reviews/milestone_progress.md` 記錄採用版本、ACK / Delivery ID、open conditions 與整合 gate 結論；LLM POC contract 不在此 gate 範圍，不得列為阻擋條件 |
| **Developer 拆包前** | 固定允許實作的 API、hardware target 與仍待 POC 提供的驗收 evidence | 固定 Python HAL、native ABI、selected panel/config、效能量測方式與 artifact provenance | `test_spec_M3.md` 經 Designer 簽核後，Developer 才建立 `dev_progress_M3.md`；每個受影響工作包引用採用的 contract/ACK，不得引用未核准 draft 或 branch HEAD |
| **M3 delivery SHA 前** | 完成會阻擋 Pi 可重現驗收的 capability matrix、device/config/接線 evidence；M4 才決定的 TTS winner format 不阻擋 M3 | 完成 header/adapter/artifact checksum、license、build/fixture/config、P50/P95 與 lifecycle/failure evidence | 未完成項目保持 M3 acceptance blocker；POC 自驗不能取代 Core Tester 對 delivery exact SHA 的獨立驗收 |

目前 gate 狀態與下一動作只記於 `docs/reviews/milestone_progress.md`，不以本規劃中的穩定規則推定已放行。

### 5.3 排除項目

* 不整合真實 ASR / TTS / LLM ；硬體測試使用固定 PCM / image fixture 或診斷 worker。
* 不等待 LLM POC contract 才開始或驗收 M3；LLM model / runtime / child protocol 屬 M4 entry gate。
* 不實作 wake daemon、MQTT 或 Vision 模型。
* 不實作正式版面資產、開關機動畫、狀態轉場或視覺 polish ；這些屬 M7 後續規格修訂與實作範圍。
* 不加入 LED 表達、touch、OSD overlay 或一 pin 多訂閱者。
* 不以 Windows 測試結果替代 Pi 硬體驗收。

### 5.4 可重複驗收

1. 執行完整純軟體 suite，再於 Raspberry Pi 5 執行：

```bash
python -m pytest -v
python -m pytest -v -m rpi tests/milestones/test_m3_rpi_hal.py
```

2. Pi 驗收至少證明：
* AudioInput 在 timeout 內產生格式與 frame size 正確的 PCM ；AudioOutput 完整消費固定 fixture。
* Camera 依 config 產出合法 JPEG / RGB / YUV bytes 與正確尺寸。
* GPIO register / debounce / unregister / output 行為在指定測試 pin 可重複。
* Display 一次 intent 僅做一組 clear / write / show ；fullscreen ownership、release 與 NullDisplay (0,0) 行為正確。
* 固定離線字型、Normal 的 StatusBar + Main 與 Fullscreen Blank 可讀；startup / shutdown 使用 stable owner 與全黑畫面，且 display failure 不改變主流程或 exit code。
* 拔除或指定不存在的 audio / display / camera device 後可觀察 null fallback 與 `capability=false` ；GPIO failure 依 required policy 收斂且沒有 NullGPIO。

3. 需要人工觀察的喇叭 / OLED 項目使用固定 fixture 與 checklist，結果記錄硬體型號、config hash、測試時間與 pass / fail ；人工結果不取代可自動檢查的 buffer / 呼叫順序。

4. Button 語意驗收（GPIO 實體 pin，對話按鈕）至少證明：
   * 短按（`short_press_min_ms` ≤ `duration_ms` < `long_press_min_ms`）於 IDLE 產生 `ButtonPressed` Signal，觸發 WAKE 並進入 listen。
   * 短按於非 IDLE 進行中 session（PERCEPTION / THINK / ACTION）產生 `InterruptRequested` 行為，session 收斂後回 IDLE。
   * 長按（`duration_ms` ≥ `long_press_min_ms`）於任意狀態產生 `ShutdownRequested` Signal，App graceful shutdown，exit code 0。
   * 短按於 ERROR 狀態（recovery 已完成或無 recovery）直接進 WAKE，開始新 session。
