## M4-ERR boundary

USER決定在M4B與M4C之間加入`M4-ERR`，關閉底層error handling，而不是把發現的問題縮成
M4C內單一ASR修補。其範圍包含通用outcome taxonomy、native／adapter／worker／State Manager間
不失真的錯誤傳遞、backend usability、Level 1／2／3、Resource Manager rebuild、sanitized
diagnostic cause、privacy與startup／shutdown；並覆蓋M4產品實際使用的Button、ASR、LLM、
TTS／Audio、Display、Conversation及recovery路徑。

`INFERENCE_REJECTED`是觸發此工作切分的第一個具體缺口：目前native ASR內部錯誤被錯誤包成
可重試request rejection。M4-ERR須把這類狀況改成system fault，並檢查其他production component
是否存在同類lossy／broad exception mapping。未來milestone的新元件必須mapping到完成後的通用
contract，不重開另一套error framework。

M4-ERR獨立走`Design → Test Spec → Developer → Verify`，在Pi以待提交相同bytes完成component、
fault-injection、recovery與fatal-exit驗證。M4C不重做其完整taxonomy矩陣，只以whole-product代表性
場景證明composition正確使用已驗證契約。

### M4-ERR design entry

M4-ERR Design entry不等待M4C-SS實驗結果，因streaming方案選擇不改變底層error taxonomy的完整性
要求。其上游已滿足：M4A／M4B Accepted、USER明確建立M4-ERR、第一個lossy mapping可由現行ASR
實作定位，且M4C whole-product scenario已列出消費契約。M4C-SS request送達後，current owner即可
切到M4-ERR Design；M4C仍維持Test Spec／Developer closed，直到M4-ERR Accepted且M4C-SS Closed。
