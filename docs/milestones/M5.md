# M5.tool／M5 — 有限工具能力與 MQTT 雙向訊息

產品範圍與驗收問題以本文件為準；具體契約見 [M5.tool 設計](../implement/ch_m5_tool.md)。
當前 entry 只見 [current](../status/current.md)。
順序：`ALPHA → M5.tool → M5 MQTT → M6 Look → M7 → BETA`。

## 1. 已確認決策

- Wake 移出目前工作，BETA 前才重新評估是否加入；button 繼續提供語音入口。
- 先限於命令派發與 Look 觀察，不開發通用 reasoning loop、query action 或任意工具串接。
- 模型選語意能力，Reasoner 驗證並決定 Core action／route；SDK 不自動執行 handler。
- 同一 native Conversation 保留前文，不重送整份 history；Conversation replacement 會失去
  前文，即使產品 Session 相同。此為明確 error path，不另開記憶研究。
- MQTT 外部 response 與主動通知經 buffer／read 進入對話，不是 handler return，也不回寫
  舊 ActionCompleted。M5 必須同時完成發送與接收。
- Look 是下一輪 perception，不是 fire-and-forget 命令；該輪只啟動 look，不等 listen。
- 本輪不考慮 read／Look 交錯，不為此設計額外矩陣。

## 2. M5.tool — 工具能力開發與驗證

### 2.1 價值與範圍

先回答真實 Gemma 能否選對能力、觸發固定遠端連線命令並根據物件觀察接續回答，將模型問題與
MQTT／硬體問題分開。只 mock handler 與視覺輸入，不能 mock 模型意圖或回答取得品質 PASS。

包含 USER 選定的短版 **c2** 能力 prompt、兩欄模型語意 schema（`intent`、`text`）與 Core
固定命令映射／驗證、Reasoner 路由、`mock.send` handler（M5.tool 固定參數
`message="啟用遠端連線"`）、真實 Look worker 接 mock Camera／Vision、tool 固定語音回饋、
必要 profile／child protocol 及 admission 更新。沿用真實 Gemma、Audio／TTS、button 與
selected Display。

未來 M5 產品配置中，Whisper ASR `initial_prompt` 依 USER 指示固定為 `遠端連線`（取代舊詞表，
不回寫已 Accepted 的 ALPHA 證據；本階段依 USER 決定移除專用 ASR 單句詞彙測項，亦不在啟動或
測項中加入重複的 prompt／text digest 檢查）。

```text
listen → Gemma 輸出兩欄 JSON 選 tool → child/Core 固定映射 mock.send("啟用遠端連線") 並忽略模型 text
       → 驗證 → tool dispatch（僅一次）→「已送出。」或「未能確認送出，請稍後再試。」→ listen

listen → Gemma 輸出兩欄 JSON 選 look → 忽略模型 text，speak「我看一下。」→ 下一輪只 look
       → mock 物件觀察＋接續提示 → 原 Conversation 回答 → speak → listen
```

模型只輸出 `intent` 與 `text`；`tool` 與 `look` 的模型 `text` 絕不作為 `SAFE_TEXT`、Display
文字或 TTS 播音。Core 單向將 `intent="tool"` 映射為單一固定、有界命令（M5.tool 為 `mock.send`
配固定 `message="啟用遠端連線"`，無 MQTT IO），絕不接受模型自選工具名稱、MQTT topic、payload
或自由參數。固定派發回饋不再呼叫模型；成功只代表命令已派發，不代表遠端連線實際建立或外部動作完成。
Look 回答屬下一個產品 turn，維持每 turn 一次推論，不新增 TOOL state。
產品路徑統一稱為 **answering**（基本回答）、**dispatching**（`tool` 意圖→Core 固定映射→
ToolRegistry handler→固定回饋→`listen`）與 **observing**（`look` 意圖→固定準備語→下一輪
`look` perception→原 Conversation 回答）。Look 不作為 ToolRegistry handler。具體邊界見
[M5.tool 設計 §2.1](../implement/ch_m5_tool.md#21-m5tool-的能力)。

### 2.3 驗收問題

| 問題 | 必須證明的行為 | 產品價值 |
| :--- | :--- | :--- |
| 能力選擇與邊界 | 真實模型對一般聊天選 `speak`、結束選 `end`；明確要求啟用遠端連線（含正向換句話說）選 `tool`；辨識眼前物件問題選 `look`；詢問顏色選 `speak` 誠實說明無法辨識 | 能使用固定能力、不誤觸副作用且不捏造視覺能力 |
| 派發映射與驗證 | 模型僅輸出兩欄（`intent`, `text`）；Core 固定映射 `tool` 為 `mock.send("啟用遠端連線")`；未知名稱／非法內部語意或 `source="look"` 再次選 `look`/`tool` 在 handler 前拒絕；單次合法意圖只執行一次 | 模型不決定工具名稱／參數，不錯發或重複送出 |
| 派發回饋與文字抑制 | `tool`/`look` 的模型 `text` 不作為 `SAFE_TEXT`、Display 或 TTS 播音；由應用程式播報固定準備語／派發回饋；成功只代表命令已派發，不宣稱遠端連線已建立；不增加推論，之後 `listen` | 忽略模型過早宣稱或虛構描述，狀態誠實且可繼續操作 |
| Look 接續 | look-only 不等待新語音，原 Conversation 理解先前問題 | 觀察能接回對話 |
| 回答有依據 | 同一物件問題配兩種 mock 物件觀察（`OBS_BOOK`/`OBS_CUP`），答案隨觀察改變且不提供未支援能力（如讀書內容）；空偵測不等於系統錯誤且繼續對話；顏色問題說明無法辨識 | 排除忽略結果、跨輪殘留與捏造 |
| 錯誤處理 | Look error／timeout 可回覆後 listen；Conversation 遺失則放棄舊問題，不 replay | 失敗後可用、不錯接上下文 |
| 中斷與停止 | 派發或 Look 等待時中斷，無遲到播音／新 Session 污染；正常 stop 可完成 | 新增路徑可取消且無殘留 |
| 原對話回歸 | 一般回答、同 Conversation 接續、明確結束及直接受影響 streaming speak | 不破壞已交付主線 |
| 首輪效能 | 新 Conversation 首次合法推論的 native `runtime_prefill_tokens <= 128`；記錄首輪與後續 turn 的首段／terminal 等待，辨識能力 prompt 的代價 | 保留既有首輪效能分界，不以後續低 prefill 掩蓋首輪等待 |

Tester 可合併情境，不做所有 state × failure × tool 組合。自動檢查路由／次數／資料流，
真實語意與語音／Display 體驗保留適用人工判讀。Pi 上以相同待提交內容完成適用自動、
整合與真人操作；觀察新 Conversation 首輪與同 Conversation 後續 turn 的 prefill、
首段／terminal 等待及新增路徑延遲，不加未經實測的數值效能門檻。不重開 ALPHA。
首次模型未選中能力時可調整 prompt／支援句型再驗；但只靠注入語意通過 Core 管線，
或僅執行單次隔離 prompt 診斷，不能取得真實模型產品路徑 `FLOW` 的 PASS。先前單次 c2 診斷中否定遠端連線請求
（「先不要啟用遠端連線」）選 `end` 的結果僅保留於開發診斷歷史；依 USER 決定，該否定句已移出本輪對話與測試驗收範圍，不列為現行驗收條件或額外負向命令矩陣。Tester 以少量能區分正確選擇、
固定命令映射與正向換句話說的情境裁定。
public evidence 只留必要 boolean、count、stable code；內容只供 private 判讀。
不計算或驗證 source／config／prompt／artifact digest 作為 startup／測項；需要確認跨機檔案一致性時，
只在傳輸邊界由 operator 執行一次獨立檢查。

## 3. M5 MQTT — 發送與外部訊息接收

### 3.1 範圍與資料流

價值：把已驗證的派發能力接到真實外部系統，讓回應與主動通知能進入產品對話。

```text
listen → Reasoner → action/tool → MQTT handler → publish → 派發回饋 → listen

外部 response／主動通知 → MQTT adaptor → buffer → ExternalMessageArrived
                       → read → Reasoner → action
```

- 發送只承諾 wire 契約的派發結果，不等待外部業務完成；不自動重送結果不確定的命令。
- Adaptor 驗證 wire，轉成 Ch 7 的 text＋metadata；raw payload／credential 不進 Event Bus。
- IDLE 的合法訊息觸發 external-message wake，新 Session 第一輪 read。
- 活躍 Session 的訊息依 active read window／pending 規則歸屬；M5 MQTT profile 在下一個候選為
  listen 的 eligible PERCEPTION boundary，由 StateManager 只看 opaque pending IDs 確定性替換為
  read-only。Payload 只能由 read 消費，不能在 THINK 偷讀 buffer；current operation與Look flow不被打斷。
- 外部 response 可在原 Conversation 承接指令；若已是新 Session，訊息本身須有足夠
  來源及結果描述，不能假設舊前文仍在。只有實際 domain 需要時才加入 request reference，
  不新增通用 correlation reasoning loop。
- Arrival order、consume、overflow、正常結束 flush-to-wake、interrupt／error discard
  沿用 [Ch 7](../implement/ch07_external_message.md)。
- Broker availability 是 runtime 狀態，不改 startup-static capability map。

### 3.2 此階段才需要固定的輸入

M5.tool Accepted 後，固定 broker、認證配置、topic namespace、第一個實際工具 domain
schema、publish 成功語意、QoS／retain、重送與重複訊息政策，再於 protocol.md 寫公開
wire schema。Pending scheduling 已依 [AR_impl_M5_MQTT_I](../reviews/history/AR_impl_M5_MQTT_I.md)
固定為 deterministic read-only；read wrapper、輸入上限與 prompt disposition 由 native POC 決定。
其餘未選定輸入不假造端點，也不阻擋已 Accepted 的 M5.tool。

### 3.3 驗收與排除

Pi＋測試 broker 驗證真實發送、外部 response 與主動通知、IDLE／活躍 Session read、
無效 payload 拒絕、斷線／重連時主對話可用與所選 wire policy 的重複訊息行為。
針對實際變動做 buffer／read 回歸，沿用適用證據，不重跑整套 M5.tool 品質實驗。
不以 mock 代替外部 round trip；不把完成 publish 等同 M5 完成。
排除 read／Look 交錯、Wake、真實 Vision、外部結果回寫舊 ActionCompleted、跨 Session 記憶。
