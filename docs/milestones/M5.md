## 1. 已確認決策

- Wake 移出目前工作，BETA 前才重新評估是否加入；button 繼續提供語音入口。
- 先限於命令派發與 Look 觀察，不開發通用 reasoning loop、query action 或任意工具串接。
- 模型選語意能力，Reasoner 驗證並決定 Core action／route；SDK 不自動執行 handler。
- 同一 native Conversation 保留前文，不重送整份 history；Conversation replacement 會失去
  前文，即使產品 Session 相同。此為明確 error path，不另開記憶研究。
- MQTT 外部 response 與主動通知經 buffer／read 進入對話，不是 handler return，也不回寫
  舊 ActionCompleted。M5 必須同時完成發送與接收。
- Look 是下一輪 perception，不是 fire-and-forget 命令；該輪只啟動 look，不等 listen。
- 本輪不考慮 read／Look 交錯，不為此設計額外矩陣。

## 2. M5.tool — 工具能力開發與驗證

### 2.1 價值與範圍

先回答真實 Gemma 能否選對能力、提供有效參數並根據觀察接續回答，將模型問題與
MQTT／硬體問題分開。只 mock handler 與視覺輸入，不能 mock 模型意圖或回答取得品質 PASS。

包含新能力 prompt、語意 schema／驗證、Reasoner 路由、`mock.send` handler、
真實 Look worker 接 mock Camera／Vision、tool 固定語音回饋、必要 profile／child protocol
及 admission 更新。沿用真實 Gemma、Audio／TTS、button 與 selected Display。

```text
listen → Gemma 選 mock.send → 驗證 → tool dispatch
       →「已送出。」或「未能確認送出，請稍後再試。」→ listen

listen → Gemma 選 look → speak「我看一下。」→ 下一輪只 look
       → mock 觀察＋接續提示 → 原 Conversation 回答 → speak → listen
```

固定派發回饋不再呼叫模型；成功只代表派發，不代表外部動作完成。Look 回答屬下一個
產品 turn，維持每 turn 一次推論，不新增 TOOL state。

### 2.3 驗收問題

| 問題 | 必須證明的行為 | 產品價值 |
| :--- | :--- | :--- |
| 能力選擇 | 真實模型對一般聊天直接回答，明確送訊選 mock.send 並保留內容，看圖要求選 Look | 能使用能力且不誤觸副作用 |
| 派發驗證 | 未知名稱／非法參數在 handler 前拒絕；單次合法意圖只執行一次 | 不錯發或重複送出 |
| 派發回饋 | 成功才說已送出；失敗不稱成功；不增加推論，之後 listen | 狀態誠實且可繼續操作 |
| Look 接續 | look-only 不等待新語音，原 Conversation 理解先前問題 | 觀察能接回對話 |
| 回答有依據 | 同一問題配兩種 mock 觀察，答案隨觀察改變；空偵測不等於不存在 | 排除忽略結果與捏造 |
| 錯誤處理 | Look error／timeout 可回覆後 listen；Conversation 遺失則放棄舊問題，不 replay | 失敗後可用、不錯接上下文 |
| 中斷與停止 | 派發或 Look 等待時中斷，無遲到播音／新 Session 污染；正常 stop 可完成 | 新增路徑可取消且無殘留 |
| 原對話回歸 | 一般回答、同 Conversation 接續、明確結束及直接受影響 streaming speak | 不破壞已交付主線 |

Tester 可合併情境，不做所有 state × failure × tool 組合。自動檢查路由／次數／資料流，
真實語意與語音／Display 體驗保留適用人工判讀。Pi 上以相同待提交內容完成適用自動、
整合與真人操作；觀察新增兩輪延遲，不加數值效能門檻。不重開 ALPHA。
public evidence 只留必要 boolean、count、stable code；內容只供 private 判讀。
不計算或驗證 source／config／prompt／artifact digest 作為 startup／測項。

## 3. M5 MQTT — 發送與外部訊息接收

### 3.1 範圍與資料流

價值：把已驗證的派發能力接到真實外部系統，讓回應與主動通知能進入產品對話。

```text
listen → Reasoner → action/tool → MQTT handler → publish → 派發回饋 → listen

外部 response／主動通知 → MQTT adaptor → buffer → ExternalMessageArrived
                       → read → Reasoner → action
```

- 發送只承諾 wire 契約的派發結果，不等待外部業務完成；不自動重送結果不確定的命令。
- Adaptor 驗證 wire，轉成 Ch 7 的 text＋metadata；raw payload／credential 不進 Event Bus。
- IDLE 的合法訊息觸發 external-message wake，新 Session 第一輪 read。
- 活躍 Session 的訊息依 active read window／pending 規則歸屬；Reasoner 只看 pending
  metadata 來安排後續 read，payload 只能由 read 消費，不能在 THINK 偷讀 buffer。
- 外部 response 可在原 Conversation 承接指令；若已是新 Session，訊息本身須有足夠
  來源及結果描述，不能假設舊前文仍在。只有實際 domain 需要時才加入 request reference，
  不新增通用 correlation reasoning loop。
- Arrival order、consume、overflow、正常結束 flush-to-wake、interrupt／error discard
  沿用 [Ch 7](../implement/ch07_external_message.md)。
- Broker availability 是 runtime 狀態，不改 startup-static capability map。

### 3.2 此階段才需要固定的輸入

M5.tool Accepted 後，固定 broker、認證配置、topic namespace、第一個實際工具 domain
schema、publish 成功語意、QoS／retain、重送與重複訊息政策，再於 protocol.md 寫公開
wire schema。也須完成 read 的投影、輸入上限與 pending 排程及 Test Spec。
以上未在本次對話選定，不假造端點，也不阻擋 M5.tool。

### 3.3 驗收與排除

Pi＋測試 broker 驗證真實發送、外部 response 與主動通知、IDLE／活躍 Session read、
無效 payload 拒絕、斷線／重連時主對話可用與所選 wire policy 的重複訊息行為。
針對實際變動做 buffer／read 回歸，沿用適用證據，不重跑整套 M5.tool 品質實驗。
不以 mock 代替外部 round trip；不把完成 publish 等同 M5 完成。
排除 read／Look 交錯、Wake、真實 Vision、外部結果回寫舊 ActionCompleted、跨 Session 記憶。
