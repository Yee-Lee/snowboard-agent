# M5 規劃


## 7. M5 ── 外部訊息與工具

### 7.1 範圍

* 實作 MQTT adaptor 的連線、格式驗證、runtime availability 與 `input_events/external_message.ingest()` 接面。
* 在 `docs/protocol.md` 定義公開 MQTT topic、版本、payload、錯誤處置與相容性規則。
* 完成 MQTT message → buffer → ExternalMessageArrived → read → reasoner → action 的整合流程。
* 實作至少一個實際 ToolRegistry handler，經 SM → action/tool → ToolRegistry 派發；若控制 GPIO，必須走 GPIO HAL。
* 驗證 pending metadata、read window、overflow、flush-to-wake、discard 與 MQTT reconnect 不改動 startup-static capability map。

### 7.2 相依

* M4a、M4b、M4c 已在同一產品 delivery exact SHA 驗收通過，M4 conclusion 為 Accepted；M5 必須引用該 SHA。
* MQTT broker、topic namespace、認證與第一個實際 tool 的 domain schema 已確認。
* 對外 MQTT wire schema 已 review。

### 7.3 排除項目

* Tool 維持 fire-and-forget；不把實際物理結果回寫本次 `ActionCompleted` 。
* 不加入 query action、tool result 二次推論或 correlation-based reasoning loop。
* 不在 SM / Reasoner 中保存外部訊息 payload。
* 不把 broker connection 狀態寫入 startup-static capability map。

### 7.4 可重複驗收

1. 使用本機測試 broker 與 Raspberry Pi 5 執行：

```bash
python -m pytest -v
python -m pytest -v -m rpi tests/milestones/test_m5_external_tools.py
```

2. 驗收至少證明：
* 不合法 wire payload 在 adaptor 丟棄並記 WARNING，不進 Event Bus 或 buffer ；若公開 protocol 另定回覆訊息，則只依該 schema 回覆。
* 合法訊息依 arrival order 消費；overflow 三種 policy、pending、flush 與 discard 符合 Ch 7。
* broker 斷線只使 `is_available()` / 連線狀態降級，主對話與 capability map 不變。
* 模型只能看到 tool schema 並產 intent ；handler只由 Tool action 執行一次。
* 未知 tool / 非法 arguments 在 handler 前被拒絕；派發成功後外部失敗以新訊息處理。
* 測試 log 不含 MQTT password、完整 message text 或 tool arguments。
