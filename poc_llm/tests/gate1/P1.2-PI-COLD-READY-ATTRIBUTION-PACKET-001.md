- **Trigger**: Qwen Gate 2A first cold child did not emit READY inside the unchanged 10-second

  bounded operational READY observation window so the remaining Gate 2A work can continue.

## 1. Purpose and future value

P1.2 exists to characterize and ultimately solve true product cold boot. Its deliverable is not a
weaker P1 threshold. It must identify why an Engine that was previously observed READY in about 3.5
seconds can require about 19.2 seconds when started after a reboot without a just-in-time full model
read. The result should inform future Core integration, service startup policy, artifact staging,
memory/cache behavior, Engine capacity selection and recovery design.

## 2. Preserved observations

All observations used the same Raspberry Pi 5 4 GB, Debian 13 aarch64, LiteRT-LM v0.16.0, Qwen
artifact, `engine_max_num_tokens=512`, four CPU threads, swap zero, offline namespace, immutable prior
receipt and clean execution source `ed7aaca2e187b2287d442d6841e1ab2610b67570`. No observation
performed a full model hash.

The two diagnostics are reproducible observations, not P1 reruns. They establish that the delay is
inside native `Engine()` construction. They do not establish whether page residency, storage I/O,
memory pressure, Engine capacity or another runtime-owned mechanism is causal.

## 3. Deferred experiment matrix

When P1.2 resumes, use a fresh boot per cell and measure page residency/I/O, memory and native Engine
time. First compare 512-token Engine construction with and without an explicit non-hashing sequential
read. Then compare a true-cold 256-token Engine only if the product prompt/KV envelope remains valid.
Add the combined 256/pre-read cell only when needed to distinguish an interaction. Preserve the 10
second P1 decision rule and never count a diagnostic observation as acceptance credit.
